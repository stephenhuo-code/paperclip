# Feature Specification: 引导脚本新增组织

**Feature Branch**: `feat/keycloak-sso`

**Created**: 2026-10-16

**Status**: 待办（plan 待确认，尚未开发）

**Input**: first-run.sh 支持新增组织：原脚本只初始化第一个组织（Keycloak 组织 + Paperclip 公司 + 关联）。给脚本加参数（如 `--add-org`），交互式引导运维人员新建一个 Keycloak 组织（名称、别名、邮箱域名）和对应的 Paperclip 公司，把"组织 → 公司"追加到映射中（保留已有映射，不覆盖），然后重新部署使配置生效。可重复执行，已完成的步骤跳过。同时修正首次初始化流程：重写映射时保留其他组织的映射。员工管理仍在 Keycloak 管理台。

**Related**: [003](../003-first-run-setup/spec.md)（首次初始化引导脚本）

## Clarifications

### Session 2026-10-16

- Q: 新组织的公司由谁管理？ → A: 只由现有实例管理员担任 owner；之后在 Paperclip"公司设置 → 成员"中把该组织负责人提升为管理员（负责人需先企业登录一次）。脚本不为新组织创建任何人员账号。

## 现状与要改的部分

企业登录本身已支持多个组织：映射表中每个"Keycloak 组织 → Paperclip 公司"都会生效，员工按所在组织自动加入对应公司。但目前：

- 引导脚本只处理部署配置里的那一个组织；新增组织要运维人员手工在 Keycloak 管理台建组织、在 Paperclip 建公司、查公司 ID、登录服务器编辑配置文件、再重新部署。
- 首次初始化流程会把映射表整体重写为只含第一个组织，重新运行时会**删掉**其他组织的映射。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新增一个组织及其公司 (Priority: P1)

平台已完成首次初始化。运维人员在服务器上以"新增组织"方式运行引导脚本，按提示输入组织和公司信息，结束后该组织的员工即可用企业账号登录进入新公司。

**Independent Test**: 在已初始化的实例上以新增组织方式运行脚本，输入新组织名称、别名、邮箱域名和公司名称；结束后，在 Keycloak 中把一个员工加入新组织，该员工企业登录直接进入新公司；原组织员工登录仍进入原公司。

**Acceptance Scenarios**:

1. **Given** 已完成首次初始化，**When** 以新增组织方式运行脚本并输入组织名称、别名、邮箱域名、公司名称和 Paperclip 管理员的应急密码，确认后，**Then** Keycloak 中创建该组织，Paperclip 中创建该公司（实例管理员为 owner），映射表追加这一条且原有条目保持不变，平台重新部署并通过健康检查。
2. **Given** 同上，**When** 脚本结束，**Then** 屏幕给出下一步说明（在 Keycloak 把员工加入新组织），且不显示任何密码。
3. **Given** 运行中途在确认时回答"否"，**When** 脚本退出，**Then** 不做任何改动。
4. **Given** 新公司已开通，**When** 该组织负责人首次企业登录后，**Then** 实例管理员可在 Paperclip 中把他提升为该公司管理员；脚本结束时的说明中给出这一步。

### User Story 2 - 重复执行与已有数据 (Priority: P2)

脚本可安全地再次运行，例如中途失败后重试，或组织 / 公司已事先手工建好。

**Acceptance Scenarios**:

1. **Given** Keycloak 中已有该别名的组织（例如手工创建），**When** 以新增组织方式运行并输入该别名，**Then** 直接使用该组织，不重复创建、不修改其设置。
2. **Given** 已有同名的 Paperclip 公司，**When** 运行脚本，**Then** 列出并让运维人员选择使用已有公司还是新建。
3. **Given** 该组织已映射到所选公司，**When** 运行脚本，**Then** 报告"已完成"，不重新部署。
4. **Given** 某一步失败，**When** 脚本退出，**Then** 给出失败原因，已完成的步骤保留；重新运行可从失败处继续。

### User Story 3 - 首次初始化不再覆盖其他组织 (Priority: P2)

已新增过组织的实例上，再次以首次初始化方式运行脚本，不会丢失其他组织的映射。

**Acceptance Scenarios**:

1. **Given** 映射表中有第一个组织和另一个新增组织，**When** 以首次初始化方式重新运行脚本，**Then** 只更新第一个组织那一条，其他组织的映射保持不变。
2. **Given** 不带新增组织参数运行，**When** 脚本执行，**Then** 行为与现在相同（003 的全部场景仍成立）。

### Edge Cases

- 别名不合法（只允许小写字母、数字和 `-`）或与已映射的其他组织重复：提示后重新输入。
- 邮箱域名已被其他组织使用：报错说明，不做改动。
- 应急密码错误：提示重新输入，最多三次后退出，不做改动。
- 尚未完成首次初始化（没有 Paperclip 管理员或首个组织未关联）：提示先运行首次初始化，不做改动。
- 平台或 Keycloak 未运行：直接报错退出，不做任何改动。
- 映射配置损坏、无法读取：报错退出，不覆盖原配置。

## Requirements *(mandatory)*

- **FR-001**: 引导脚本增加"新增组织"运行方式，由命令行参数选择；不带该参数时保持首次初始化行为。
- **FR-002**: 新增组织时交互式输入：组织名称、组织别名、邮箱域名、公司名称；改动前汇总将要做的事并请运维人员确认。
- **FR-003**: 在 Keycloak 中创建该组织（名称、别名、邮箱域名，启用）；已存在同别名组织时直接使用、不修改。
- **FR-004**: 以现有 Paperclip 实例管理员的身份创建公司，运维人员需输入该管理员的应急密码授权；密码不回显，不出现在屏幕输出、日志和命令历史中。
- **FR-005**: 把"组织别名 → 公司"追加到映射配置，保留所有已有条目；同一别名已存在时替换为所选公司，并在确认时明确提示。
- **FR-006**: 映射有变化时重新部署当前版本使之生效；没有变化时不重新部署。
- **FR-007**: 首次初始化流程更新映射时只增改首个组织那一条，保留其他组织的条目。
- **FR-008**: 每一步执行前检查是否已完成，已完成则跳过并说明；可重复执行。
- **FR-009**: 不涉及员工管理：不创建任何人员账号、不修改组织成员、不分配角色；新公司的 owner 是现有实例管理员。
- **FR-010**: 新增的组织不由部署自动维护，之后在 Keycloak 管理台的修改不会被部署恢复。

## Success Criteria *(mandatory)*

- **SC-001**: 运维人员 5 分钟内完成一个新组织的开通，无需打开 Keycloak 管理台创建组织、无需手动编辑配置文件。
- **SC-002**: 新组织开通后，其成员首次企业登录即进入对应公司；已有组织成员的登录结果不受影响。
- **SC-003**: 任意顺序、任意次数运行首次初始化和新增组织，映射表中不会丢失已开通组织的条目，也不会产生重复的组织或公司。

## Assumptions

- 平台已完成首次初始化（003）：有 Paperclip 实例管理员和首个组织的关联。
- 所有组织在同一个 Keycloak realm 中；每个组织的员工通常不重叠，`agent-creator` 角色对其所属的每家公司都生效。
- 新公司的 owner 是现有实例管理员（公司创建者）；Paperclip 中的公司管理员仍在 Paperclip 里设置。
- 删除组织、修改已有组织的名称或域名不在范围内，在 Keycloak 管理台操作。
- 登录页品牌（平台名称、logo）全实例共用，不按组织区分。
